# RLM MCP Server Configuration Guide

## Environment Variables

The `npm start` commando runs the server already as background process with `pm2` and logs in `tmp/server.log` see: `prod.config.json` for more info about the production setup.

### Optional (Already default for production)

| Variable | Description | Default |
|----------|-------------|---------|
| `PORT`   | HTTP server port (used with `--http` flag) | `3000` |

## Transport Configuration

### Stdio Mode (Default)

Best for local MCP clients (Claude Desktop, Roo Code, etc.):

```bash
node dist/index.js
```

The MCP client launches the server as a subprocess via stdio. **Do not run this command interactively in an agent session** – it will block.

### HTTP Mode

Start an HTTP server that accepts MCP requests over HTTP:

```bash
node dist/index.js --http --port=3000
```

**Current behavior**: Each HTTP request creates a new, stateless server instance. Sessions are **not** shared across requests unless you modify the server to reuse a single instance (see Shared Sessions below).

HTTP Endpoints:
- `POST /mcp` – MCP protocol endpoint
- `GET /health` – Health check (returns `{status: "ok"}`)
- `GET /info` – Server information (name, version, tool list)

#### When to Use HTTP Mode

- **Shared sessions** across multiple agents or processes
- **Testing** with tools like `curl` or MCP inspector
- **Remote access** from a client that supports HTTP MCP transport
- **Background processing** where the server runs independently of any single agent

#### Shared‑Session Considerations

The HTTP server uses a singleton `SessionManager` that is shared across all requests. This means sessions are automatically shared across multiple agents as long as they use the same `session_id` in tool calls.

**How shared sessions work**:
1. Start the HTTP server as a background process (e.g., `npm start`).
2. All agents connect to the same HTTP endpoint.
3. Agents supply the same `session_id` parameter in their tool calls (e.g., `{"session_id": "shared"}`).
4. The `SessionManager` will store contexts, variables, and answers under that session ID, making them accessible to all agents using that ID.

**Default behavior**: If no `session_id` is provided, the server uses `'default'`. Multiple agents that omit `session_id` will share the same default session.

**Isolation**: To keep agents isolated, give each a unique `session_id`.

**Transport‑level sessions**: The MCP transport itself is stateless (`sessionIdGenerator: undefined`). Session persistence is handled entirely by the application‑level `SessionManager`.

## Resource Limits

Actual limits are defined in [`src/constants.ts`](src/constants.ts):

| Constant | Value | Description |
|----------|-------|-------------|
| `CHARACTER_LIMIT` | 100,000 | Maximum response size |
| `MAX_REPL_OUTPUT` | 50,000 | Maximum REPL output per execution |
| `MAX_CONTEXT_PREVIEW` | 5,000 | Default preview length for `rlm_get_context_info` |
| `MAX_SEARCH_RESULTS` | 500 | Maximum search results returned |
| `DEFAULT_CHUNK_SIZE` | 10,000 | Characters per chunk (fixed‑size strategy) |
| `DEFAULT_OVERLAP` | 200 | Overlap between chunks |
| `DEFAULT_LINES_PER_CHUNK` | 100 | Lines per chunk (by_lines strategy) |
| `CODE_EXECUTION_TIMEOUT_MS` | 30,000 | JavaScript execution timeout (30 seconds) |
| `SESSION_TIMEOUT_MS` | 3,600,000 | Inactive session timeout (1 hour) |
| `MAX_SESSIONS` | 100 | Maximum concurrent sessions |

These limits are enforced by the server; clients cannot override them.

## Security Considerations

### API Keys

No external LLM API keys are required or used by this server.

### Code Execution Sandbox

The REPL environment (`rlm_execute_code`) executes JavaScript code generated by the LLM:

- Code runs in a Node.js sandbox using `eval` within a restricted function.
- Network access, file system access, and process spawning are **not** explicitly blocked but are limited by the sandbox's scope (no `require`, no `fetch` by default).
- A timeout (`CODE_EXECUTION_TIMEOUT_MS`) prevents infinite loops.
- The sandbox provides only the functions listed in the REPL Environment Functions table (see `AGENTS.md`).

### Input Validation

- All tool inputs are validated via Zod schemas (`src/schemas/tools.ts`).
- Context size is **not** limited – the RLM pattern is designed for arbitrarily long contexts.
- Individual tool parameters have reasonable defaults and bounds (e.g., `max_results` capped at 500).

## Common Configuration Scenarios

### Single‑Agent Local Usage (Recommended)

1. Configure your MCP client (Claude Desktop, Roo Code, etc.) to launch the server via stdio (see `README.md`).
2. The agent uses the tools directly; no environment variables or command‑line flags needed.

### Multi‑Agent Shared Contexts (Advanced)

1. Start the HTTP server as a background process: `node dist/index.js --http --port=3000 &`.
2. Configure each agent's MCP client to connect to `http://localhost:3000/mcp`.
3. Ensure all agents pass the same `session_id` in tool calls (or omit `session_id` to share the default session).
4. The shared `SessionManager` will keep contexts, variables, and answers accessible across all agents.

**Note**: The HTTP transport is stateless; session persistence is handled by the application‑level `SessionManager`. No modifications are required.

### Debugging / Inspection

```bash
npm run inspect
```

Launches the server with the MCP inspector for protocol debugging. **Warning**: This command is interactive and will block an agent session.

## Troubleshooting

### “Server starts but tools are not available”

- Verify your MCP client configuration points to the correct path of `dist/index.js`.
- Check that the server is running (stdio) or reachable (HTTP).
- Use `npm run inspect` to see the tool list.

### “Session data disappears between requests”

- In HTTP mode, sessions are shared across requests via the `SessionManager` singleton.
- Verify that you are using the same `session_id` in tool calls.
- If you omitted `session_id`, the default session is used (`'default'`).
- Ensure the HTTP server is running as a single background process (not restarted between requests).

### “Code execution fails with timeout”

- The sandbox has a 30‑second timeout; complex operations may exceed it.
- Break down large operations into smaller `rlm_execute_code` calls.
